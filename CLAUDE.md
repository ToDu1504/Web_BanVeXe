# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Đặt Vé Xe Khách — a bus-ticket-selling web app with four roles: Guest (Khách Vãng Lai), Customer (Khách Hàng), Staff (Nhân Viên), Admin (Quản Trị Viên). Monorepo with independent `backend/` and `frontend/` apps (no shared package manager workspace — each has its own `node_modules`/`package.json`).

## Commands

### Backend (`backend/`)
```bash
npm run dev        # nodemon server.js — dev server on PORT (.env), default 8080
npm start           # node server.js — production start
npm run db:sync     # node src/scripts/syncDb.js — sync Sequelize models to MySQL
npm run db:seed     # node src/scripts/seedData.js — seed sample data
```
No lint/test scripts exist in the backend.

### Frontend (`frontend/`)
```bash
npm run dev         # vite — dev server on http://localhost:5173
npm run build        # vite build
npm run lint          # oxlint (config: frontend/.oxlintrc.json)
npm run preview       # vite preview — serve production build locally
```
No test runner is configured in the frontend.

Run backend and frontend dev servers in separate terminals; the frontend expects the API at `VITE_API_URL` (frontend/.env), and the backend allows CORS only from `CLIENT_URL` (backend/.env).

## Architecture

### Backend — Express + Sequelize (MySQL)

- Entry: `server.js` → connects DB (`src/config/db.js`, non-fatal if DB is down), loads `src/models` (registers all Sequelize associations as a side effect), starts the two background jobs (`startExpireInvoicesJob`, `startGenerateTripsJob`), then starts `src/app.js`.
- `src/app.js` wires global middleware (cors with `credentials: true`, morgan, cookie-parser, json body) and mounts one router per resource under `/api/*`: `auth`, `users`, `invoices`, `tickets`, `routes`, `trips`, `trip-templates`, `vehicles`, `stats`, `payments`. Ends with a 404 handler and a single global error handler (`err.statusCode` / `err.message`, stack only logged server-side).
- Layering is routes → controllers → models; no service layer except `src/services/momoService.js` (MoMo request signing/callback verification, used by `paymentController.js`). Controllers are plain objects of async handlers (e.g. `src/controllers/invoiceController.js`), not classes.
- Auth: JWT is stored in an **HttpOnly cookie** (`req.cookies.token`), never in a header/localStorage. `src/middlewares/auth.js` (`protect`) verifies the cookie, loads the `User`, and checks `is_active`. `src/middlewares/role.js` (`authorize(...roles)`) gate routes by `req.user.role` (`customer` | `staff` | `admin`). Request validation goes through `src/middlewares/validate.js` with Joi schemas in `src/utils/joiSchemas.js`.
- Data model (see `src/models/index.js` for associations): `User` 1—N `Invoice` 1—N `Ticket` N—1 `Trip` N—1 `Route`, `Trip` N—1 `Vehicle`, `TripTemplate` N—1 `Route`/`Vehicle` with `TripTemplate` 1—N `Trip` (via nullable `Trip.template_id`), and `Ticket` 1—N `TicketPrint` (+ `User` 1—N `TicketPrint` via `printed_by`, aliased `PrintedByUser` to avoid clashing with `Invoice.belongsTo(User)`'s default alias). An **Invoice = one payment** (`payment_status`: pending/paid/refunded), a **Ticket = one seat** on one trip (`booking_status`: booked/cancelled). `tickets.UNIQUE(trip_id, active_seat_number)` is the DB-level guard against double booking — `active_seat_number` mirrors `seat_number` while `booking_status='booked'` and is set to `NULL` on cancel/refund, so MySQL's "multiple NULLs allowed in a unique index" behavior lets a cancelled seat be re-sold instead of permanently blocking that `(trip_id, seat_number)` pair. Always keep `active_seat_number` in sync with `booking_status` when creating or cancelling a `Ticket`. `invoiceController.create` also recomputes `ticket_price`/`total_price` server-side from `Trip.price` — never trust client-supplied prices — and a background job (`src/jobs/expireInvoices.js`) auto-cancels `pending` invoices past a TTL to release seats that were never paid for. That TTL is **split by `payment_method`**: `momo` uses `PENDING_INVOICE_TTL_MINUTES` (default 30, abandoned-checkout cleanup); `cash` (counter/pay-later bookings) uses the longer `CASH_HOLD_TTL_MINUTES` (default 120) but is also cut short — expired early — once any of its trips departs within `CASH_HOLD_DEPARTURE_BUFFER_MINUTES` (default 30), so a near-term trip is never blocked by a no-show even inside the 120-minute window. Don't recombine these into one flat TTL.
- **JSON columns need the `typeCast` in `src/config/db.js`**: MySQL sends `Vehicle.seat_layout`/`TripTemplate.days_of_week` over the wire tagged as field type `'BLOB'` (not `'JSON'`), so mysql2 hands them back as raw text and Sequelize's `DataTypes.JSON` doesn't re-parse for MySQL — without the custom `typeCast` (which parses any `'BLOB'`/`'JSON'` field as JSON) every JSON column comes back double-encoded (a string containing `"[1,3,5]"` instead of the array `[1,3,5]`), which breaks any `.map()`/`.includes()`/`.sort()` call on it both server- and client-side. This app has no real BLOB columns, so treating every `'BLOB'` field as JSON is safe — don't remove it, and if a future column genuinely needs raw BLOB storage, special-case it there instead.
- **Booking flow is transactional**: `POST /api/invoices` takes a `tickets[]` array and creates the Invoice + all Tickets inside one `sequelize.transaction()`, then decrements `trips.available_seats`. A `SequelizeUniqueConstraintError` from the double-booking constraint is caught and turned into a 409 with a Vietnamese user-facing message ("Ghế ... đã được đặt"). Cancelling an invoice, and marking one `refunded`, run in the same transactional pattern and must add the seats back to `trips.available_seats`. When touching booking/cancellation code, preserve this transaction + seat-count bookkeeping — it's the mechanism that prevents overselling.
- **Đặt vé hộ khách (staff/admin booking on a customer's behalf)**: `createInvoice`'s Joi schema accepts an optional `customer_id`; `invoiceController.create` only honors it when `req.user.role` is `staff`/`admin` (a plain `customer` sending `customer_id` gets a 403, not a silent ignore) and 404s if that user doesn't exist — omitting it keeps the old behavior (invoice owned by `req.user.id`). Staff resolve that id via two staff/admin-only endpoints on `userController` — `GET /api/users/customers/search?phone=` (returns only `role: 'customer'` matches, safe fields only) and `POST /api/users/customers` (finds-or-creates a customer by phone; 409s if the phone belongs to a `staff`/`admin` account; a newly-created customer gets a placeholder email `khach.<phone>@quayve.local` when none is given and a random unusable password — both routes are declared in `user.routes.js` **before** its blanket `router.use(protect, authorize('admin'))`, since staff otherwise has zero access to `/api/users/*`). Frontend: `customer/BookTicket.jsx` renders a "Khách hàng nhận vé" block only when `user.role !== 'customer'`, disables submit until a customer is resolved, and sends the chosen id as `customer_id`.
- **Invoice status transitions are restricted**: `invoiceController.updateStatus` only allows `pending → paid` and `paid → refunded` (see `ALLOWED_STATUS_TRANSITIONS`); `refunded` is terminal. Don't loosen this without a reason — it exists because staff could otherwise set nonsensical states like `paid → pending`.
- **Self-service cancellation enforces a 24h-before-departure cutoff** (`CANCELLATION_CUTOFF_HOURS` in `invoiceController.js`/`ticketController.js`, matches the copy on the Cancellation Policy page) for `req.user.role === 'customer'` only — staff/admin cancelling on a customer's behalf bypass it. Cancelling a `paid` invoice/ticket now marks it `refunded` (keeps the record) instead of only working on `pending` ones; cancelling a still-`pending` one still deletes it outright since nothing was collected.
- **Cancelling a Trip (`status: 'cancelled'` via `tripController.update`) cascades**: every `booked` Ticket on that trip is cancelled, and each affected Invoice is either reduced (if it also covers other trips), marked `refunded` (if it was `paid` and now has no active tickets), or deleted (if it was still `pending`). Trip create/update also validate the departure time is in the future, the vehicle isn't double-booked into an overlapping trip (`findVehicleScheduleConflict`, shared via `src/utils/tripScheduling.js`), and `available_seats` stays within `[activeTicketsCount, vehicle.total_seats]`. `vehicleController.update` blocks changing `total_seats`/`seat_layout` while the vehicle has any `scheduled`/`ongoing` trip.
- **Recurring trips**: `TripTemplate` (`route_id`, `vehicle_id`, `departure_time_of_day` "HH:mm", `duration_minutes`, `price`, `available_seats`, `days_of_week` JSON array of `Date.getDay()` values 0=Sun..6=Sat, `is_active`) lets an admin describe a weekly schedule once instead of hand-creating a `Trip` every day (managed at `/admin/trip-templates`, `ManageTripTemplates.jsx`). `src/jobs/generateTripsFromTemplates.js` turns active templates into real `Trip` rows for a rolling `TRIP_TEMPLATE_ADVANCE_DAYS`-day window (default 14), skipping instances that already exist (`Trip.template_id` + `departure_time` match), that lose to `findVehicleScheduleConflict`, or whose Route/Vehicle is inactive — it returns `{ created, skippedExisting, skippedConflict, skippedSeats, skippedInactiveResource }` rather than throwing on a single bad instance. It runs once immediately on server startup (deliberately unlike `expireInvoices.js`, which only fires on its first interval) and then every `TRIP_TEMPLATE_CHECK_INTERVAL_MS` (default 4h); admins can also force a pass via `POST /api/trip-templates/generate-now`. `Trip.template_id` is nullable with `onDelete: 'SET NULL'` — deleting a template detaches its already-generated Trips (and any Tickets/Invoices sold against them) instead of deleting them. Editing a template only affects *future* generation runs, never Trips already created.
- **Destructive admin deletes are guarded**: `tripController.delete`, `routeController.delete`, `vehicleController.delete`, and `userController.delete` all block (400, with a Vietnamese message suggesting deactivation instead) when the target still has dependent rows (Tickets on a Trip, Trips on a Route/Vehicle, Invoices on a User) — the Sequelize associations are `onDelete: 'CASCADE'`, so without this guard a delete would silently wipe paid financial history. Don't remove these checks; add an equivalent one for any new entity with cascading children.
- **Ticket printing (quầy vé) has a full audit trail, not just a boolean**: `Ticket.issued_at`/`issued_by`/`print_count` are a denormalized "last print" cache; every individual print is also recorded in `TicketPrint` (`ticket_id`, `invoice_id`, `printed_by`, `print_type`: `'original'`/`'reprint'`, `print_sequence`, `reason`) so end-of-shift reconciliation can see every print in a shift, not only the latest. `ticketController.printTicket` (`POST /api/tickets/:id/print`, staff/admin) 400s if the ticket is cancelled or its Invoice isn't `paid` yet, and requires a non-empty `reason` once `print_count > 0` (a reprint) — both the cache columns and the `TicketPrint` row are written in the same transaction. `getPrintHistory` (`GET /api/tickets/:id/prints`) returns one ticket's full print history; `getPrintLog` (`GET /api/tickets/prints?from=&to=&printed_by=`) is the shift-reconciliation report — it **force-overrides `printed_by` to `req.user.id` for any non-admin caller**, ignoring a client-supplied value, so staff can never see another staff member's prints by tampering with the query string; only `admin` may pass an arbitrary `printed_by` or omit it to see everyone's. Frontend: the print button/dialog lives in `ManageInvoice.jsx` + `TicketPrintView.jsx` (renders a QR via `qrcode.react`, purely for manual/offline reference — there is no in-app QR-scanning/verification screen), the reconciliation report is `staff/PrintReconciliation.jsx` (`/staff/print-log`).
- **Trip passenger roster**: `GET /api/trips/:id/tickets` (`tripController.getPassengers`, staff/admin) returns `{ trip, tickets }` — every Ticket on that trip (including `cancelled` ones, so staff don't mistake a cancelled seat for open capacity) with its `Invoice.payment_status`/`payment_method` and print-status columns. Rendered by the shared `TripPassengersDialog.jsx` component (used from both `staff/ViewTrips.jsx` and `admin/ManageTrips.jsx`) as an on-screen table plus a printable whole-trip **boarding manifest** (all booked passengers, no QR, no payment-status restriction — this is an internal roll-call sheet for the phụ xe, not a customer-facing ticket) with a blank "Đối chiếu" column for manual tick-marks. That manifest is rendered via a **React portal to `document.body`**, not inline inside `DialogContent` — `DialogContent` here has `max-h-[90vh] overflow-y-auto` for the on-screen table, and a `position: absolute`/visibility-toggle print block nested inside that scrollable container gets clipped during printing; portalling out of the dialog's DOM subtree avoids that entirely. Follow the same portal pattern for any future whole-page print view nested in a scrollable Dialog.
- **`tripController.getAll` (`GET /api/trips`) sorts soonest-departure-first** (`departure_time ASC`) and accepts optional `from`/`to` query params (`Op.gte`/`Op.lte` on `departure_time`) to narrow to a departure window — used by `staff/ViewTrips.jsx`'s "Khoảng thời gian" quick filter (2h / 6h / today) and its independent "Sắp khởi hành" badge (any `scheduled` trip departing within 2h, regardless of the active filter). Don't revert this to `DESC`; it was intentionally flipped so staff preparing for an imminent departure see it at the top instead of behind trips generated weeks out by `TripTemplate`.
- **Pagination is opt-in, backend-driven, and backward compatible**: every list-style `getAll` (`routes`, `vehicles`, `users`, `trips` incl. the public `search`, `invoices` incl. `getMyInvoices`, `trip-templates`) returns a bare array when the request has **no** `page` query param (used by dropdown/lookup callers that need the *full* list, e.g. the Route/Vehicle `<Select>` in `ManageTrips.jsx`), and switches to `{ data, pagination: { page, limit, total, totalPages } }` the moment `page` is present. Built on `src/utils/pagination.js` (`getPagination`, `buildPaginationMeta`). Search/filter (`search`, `status`, `role` query params) also moved server-side alongside pagination — `invoiceController.getAll`'s search is the most involved, matching invoice id, joined `User` fields (via Sequelize `$User.field$` dot-notation), and nested `Ticket.passenger_name`/`passenger_phone` (via a raw `EXISTS` subquery, since Ticket is two joins deep). Frontend: `frontend/src/components/ui/pagination.jsx` (`<Pagination pagination={...} onPageChange={...} />`) is the shared page-picker used by every list page; search inputs are debounced ~400ms before calling the API. When adding a new paginated list, follow this exact opt-in shape rather than inventing a new one.
- User-facing error/success messages throughout the backend are in Vietnamese — match that when adding new endpoints.
- **MoMo payment (sandbox)**: `src/config/momo.config.js` holds MoMo's public sandbox credentials (overridable via `MOMO_*` env vars in `backend/.env`), `src/services/momoService.js` builds/signs the MoMo `captureWallet` request and verifies callback signatures (HMAC-SHA256), `src/controllers/paymentController.js` + `src/routes/payment.routes.js` (mounted at `/api/payments`) expose `POST /momo/create/:invoiceId` (starts a payment for a `pending` invoice with `payment_method: 'momo'`), `POST /momo/ipn` (public, server-to-server callback from MoMo), and `POST /momo/verify-return` (verifies the signed query params MoMo appends when redirecting the browser back — this is what makes the flow testable on `localhost` without a public tunnel/ngrok, since IPN alone can't reach a local machine). The MoMo `orderId` encodes the invoice id (`INV{id}-{timestamp}`) so results can be matched back to an `Invoice` without a schema change. Both callback paths funnel through the same idempotent "mark invoice paid" logic in `paymentController.js`.

### Frontend — React 19 + Vite + Redux Toolkit + shadcn/ui

- Routing: `src/router/AppRouter.jsx` defines routes; `src/router/PrivateRoute.jsx` wraps role-gated routes/pages, redirecting to `/login` if unauthenticated or to `/` if `user.role` isn't in the route's `allowedRoles`. Pages are grouped by audience under `src/pages/`: `public/`, `auth/`, `customer/`, `staff/`, `admin/` — mirroring the role matrix in the README. `admin/ManageTripTemplates.jsx` (`/admin/trip-templates`, admin-only) manages recurring-trip templates and has a "Tạo Chuyến Ngay" button that force-runs the generation job.
- State: Redux Toolkit store at `src/store/store.js`. `authSlice` holds `{ user, isAuthenticated }`; `bookingSlice` holds the in-progress booking (`selectedTrip`, `selectedSeats[]`, `bookedSeats[]`) used across the trip-detail → seat-selection → checkout flow.
- API layer: one Axios module per resource under `src/api/` (e.g. `tripApi.js`, `invoiceApi.js`, `tripTemplateApi.js`), all built on the shared `src/api/axiosInstance.js`. That instance sets `withCredentials: true` (required so the HttpOnly auth cookie is sent) and has a response interceptor that dispatches `logout()` and redirects to `/login` on any 401 — don't add per-call 401 handling, it's centralized there. Every `getAll(params)` forwards `params` straight to axios as the query string — omit `params` (or the `page` key) to get the old bare-array behavior, pass `{ page, limit, search, ... }` to get the paginated shape (see backend pagination note above).
- UI: shadcn/ui primitives live in `src/components/ui/` (generated via `npx shadcn@latest add ...`, config in `components.json` — don't hand-roll a component that shadcn already provides), plus hand-rolled additions where no shadcn equivalent existed: `pagination.jsx` and `textarea.jsx` (this repo has no `components.json`-driven CLI access at present, so `textarea.jsx` was hand-written to match `input.jsx`'s styling rather than generated — prefer `npx shadcn@latest add textarea` if it becomes available again, keeping the same class conventions). Domain components live in `src/components/features/` (`SeatMap.jsx` renders `vehicles.seat_layout` JSON + `bookedSeats[]` fetched from `GET /api/trips/:id/booked-seats`; `StatsChart.jsx` uses Recharts; `TicketPrintView.jsx`/`TripPassengersDialog.jsx` are the two print surfaces described above). Shared chrome (`Navbar`, `Footer`, `AdminLayout`, `PageLayout`) is in `src/components/common/`. QR rendering uses `qrcode.react`'s `<QRCodeSVG>` (inline SVG, crisp when printed) — not the raw `qrcode` canvas package.
- Styling: Tailwind CSS v4 via the Vite plugin (no `tailwind.config.js` — see `vite.config.js` and `src/styles/globals.css`), CSS variables for theming, dark mode toggled via a `dark` class on `<html>` (see `src/hooks/useTheme.js`), preference persisted to `localStorage`. `@` resolves to `src/` (see alias in `vite.config.js` and `components.json`).
- Forms/validation: `react-hook-form` + `zod` resolvers for all forms; animations via Framer Motion (page transitions, list stagger, modal scale-in).
- **Smooth scroll + scroll-driven animation**: `App.jsx` wraps `AppRouter` in `SmoothScrollProvider` (`src/components/common/SmoothScrollProvider.jsx`), which uses `lenis/react`'s `ReactLenis` for inertia scrolling and drives GSAP's `ScrollTrigger` off Lenis's scroll events (`src/lib/gsap.js` is the single place `gsap`/`ScrollTrigger` get imported and registered — import from there, not directly from `gsap`). It self-disables (no-ops, renders children directly) when `prefers-reduced-motion: reduce`, and stops Lenis on any `/admin`/`/staff` route since `AdminLayout` scrolls its own `<main overflow-y-auto>` rather than the window. `StatCard.jsx` (used by `admin/Dashboard.jsx` and `staff/Statistics.jsx`) uses `@gsap/react`'s `useGSAP` for a count-up animation on its KPI number.
- `src/lib/utils.js` also has `exportToCsv(filename, rows)` (used by `staff/Statistics.jsx`'s "Xuất báo cáo" button) — writes a UTF-8 BOM + `sep=,` directive (Excel on Vietnamese-locale Windows defaults to `;` as the list separator without it) and force-quotes any cell that looks like a short `dd-MM`/`dd/MM` date so Excel doesn't silently reinterpret it as an en-US date. Reuse this helper for any future CSV export rather than writing a new one.
- The "Tuyến đường phổ biến" section on `public/Home.jsx` is driven by a hardcoded `FEATURED_CITIES` array (3 cities × 3 destinations each, matched against loaded `Route`s by exact origin/destination string) — it is **not** based on real booking volume and is **not** admin-configurable through any UI; changing which routes are featured means editing that array in code.

## Database

MySQL, managed through Sequelize models (not raw migrations) — schema is defined by the model files under `backend/src/models/` and applied via `npm run db:sync`. `syncDb.js` uses `sequelize.sync({ force: true })`, i.e. it **drops and recreates every table** — never run it without confirming with the user first, and always follow it with `npm run db:seed` to repopulate. **When only adding columns/tables** (e.g. the `ticket_prints` table + `Ticket.issued_at`/`issued_by`/`print_count`), prefer a one-off `sequelize.sync({ alter: true })` script instead of the destructive `force: true` sync — it applies additive schema changes without wiping existing data. The reference DDL (including the double-booking unique constraint and recommended indexes) is in [README.md](README.md). Key design point to preserve: `invoices` is one payment, `tickets` is one seat, and cancel/refund flows must keep `trips.available_seats` consistent with the sum of active (`booking_status = 'booked'`) tickets.
- `backend/src/scripts/seedData.js` seeds a realistic multi-vehicle weekly schedule for the "popular routes" (TP.HCM/Đà Lạt/Đà Nẵng): it creates `TripTemplate` rows with hand-checked non-overlapping `days_of_week`/`departure_time_of_day` per vehicle, then calls `generateTripsFromTemplates()` directly at the end of seeding so real `Trip` rows exist immediately (~300+ trips) instead of only appearing after the background job's first tick. If you edit the vehicle/template list, re-verify no vehicle ends up with two time-overlapping assignments (a quick way: fetch `/api/trips`, group by `vehicle_id`, sort by `departure_time`, and diff consecutive `arrival_time`/`departure_time` pairs).
